# Distributed Systems Labs — распространение информации

Лабораторный проект: сравнение методов распространения информации в распределённой системе из 100+ узлов.

Реализованы:

* **unicast** — доставка одному получателю;
* **multicast** — доставка группе (30 % узлов);
* **broadcast / flooding** — лавинная рассылка по графу;
* **gossip push** — периодическая рассылка случайным соседям;
* **gossip pull** — периодические опросы соседей;
* **rumor mongering** — gossip с бюджетом и обратной связью `stale`;
* **anti-entropy (push-pull)** — периодический обмен дайджестами.

Проект умеет работать в двух режимах:

1. **Симулятор** — до 400 логических узлов, виртуальное время, управляемые потери, отказы, топологии. Быстро и воспроизводимо.
2. **Docker** — реальные контейнеры (по умолчанию 110) с UDP-плоскостью данных и HTTP-плоскостью управления. Проверено на 110 контейнерах локально.

Подробный отчёт: [`docs/report.md`](docs/report.md), PDF: [`docs/report.pdf`](docs/report.pdf).  
Полные таблицы: [`docs/generated/tables.md`](docs/generated/tables.md).

## Быстрый старт

Требования:

* Go 1.24+;
* Docker Desktop (для режима Docker);
* Python 3 + `pandas`, `matplotlib`, `markdown`:

```bash
python3 -m pip install -r requirements.txt
```

Сборка и тесты:

```bash
make test
```

Симуляционные эксперименты (≈ 1–2 минуты):

```bash
make sim
make figures
make report
```

Проверка на 110 Docker-контейнерах (≈ 80 минут: контейнеры пересоздаются перед каждым прогоном):

```bash
make docker
make figures
make report
```

Полный цикл:

```bash
./scripts/run_all.sh --docker
```

## Что измеряется

* **Время распространения** — p50 / p90 / p95 / p99 / p100 от старта до первого получения сообщения.
* **Покрытие** — доля информированных узлов среди целевого множества (`coverage_intended`) и среди всех узлов, кроме источника (`coverage_total`).
* **Число сообщений** — накладные расходы алгоритма.
* **Дубли и потери** — поведение при повторных передачах и потерях.
* **Устойчивость** — влияние потерь пакетов (0–50 %) и отказов узлов (0–30 %), включая аварию во время распространения.

Потери моделируются на уровне приложения: каждый исходящий пакет с вероятностью `p` не отправляется. Отказ узла означает, что он перестаёт отправлять и принимать пакеты.

| Алгоритм | p95, 0 % потерь | p95, 50 % потерь | Покрытие, 50 % | Особенность |
|---|---:|---:|---:|---|
| unicast | 10 мс | 10 мс (40 % запусков) | 0.400 (1 получатель) | нет повторов |
| multicast | 10 мс | — | 0.478 группы | нет повторов |
| broadcast | 38 мс | 60 мс | 0.987 | самый быстрый, но хрупкий |
| gossip push | 100 мс | 348 мс | 1.000 | лучший компромисс |
| gossip pull | 520 мс | 1540 мс | 1.000 | самый медленный |

Эксперименты: 120 узлов, random-граф степени 6, 5 seed'ов, 700 прогонов в основной матрице; всего 784 симуляционных прогона и 84 прогона на 110 Docker-контейнерах.

## Структура проекта

```
cmd/node/            агент узла: UDP + HTTP
cmd/lab/             координатор: sim / docker / clean
internal/engine/     общий автомат алгоритмов, топологии, метрики
internal/sim/        симулятор с виртуальным временем
internal/agent/      сетевой агент Docker-узла
internal/dockerlab/  запуск 110 контейнеров и сбор результатов
scripts/analyze.py   графики и сводные таблицы
scripts/build_report.py  HTML/PDF из Markdown
results/*.csv        сырые результаты экспериментов
docs/img/*.png       графики
docs/report.md       отчёт
```

### Почему один автомат на два режима

`internal/engine` не знает, как доставляются пакеты. В симуляторе ему передают функцию, которая кладёт пакет в очередь событий с виртуальной задержкой. В Docker-агенте — функцию, которая отправляет JSON по UDP. Поэтому алгоритмы ведут себя одинаково, а различия результатов связаны со средой.

## Docker-режим

Координатор:

1. собирает образ `ds-lab-node:latest`;
2. создаёт сеть `dslab-net`;
3. запускает контейнеры `dslab-node-000 … dslab-node-109`;
4. публикует control-порты `127.0.0.1:18000…18109`;
5. передаёт каждому узлу карту `node id → IP:9000` (без DNS-резолвинга в горячем пути);
6. рассылает `/config`, `/start`, при необходимости `/fail`, собирает `/state`;
7. пишет CSV и очищает контейнеры.

Полезные команды:

```bash
# запустить и оставить контейнеры для отладки
go run ./cmd/lab docker -nodes 110 -build -keep -algorithms gossip_push -losses 0.2 -fails 0.1 -seeds 1

# пересоздавать контейнеры перед каждым прогоном (используется в make docker)
go run ./cmd/lab docker -fresh -nodes 110 -build ...

# переиспользовать уже запущенные контейнеры
go run ./cmd/lab docker -reuse -nodes 110 -algorithms broadcast -losses 0 -fails 0 -seeds 5

# удалить контейнеры и сеть
go run ./cmd/lab clean
```

## Ограничения

* Одно сообщение за эксперимент, без конкурирующих обновлений.
* Потери задаются на стороне отправителя; в Docker добавляются реальные фоновые потери UDP.
* Multicast реализован «звездой» от источника, без дерева и подтверждений.
* Отказы мгновенные, без постепенной деградации.
* Docker Desktop на macOS может давать собственные сетевые эффекты; на Linux-хосте цифры могут отличаться.
